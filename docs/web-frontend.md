# Web 前端设计：以创作任务为中心

第一版已实现：正式 React 页面位于 `web/src/`，HTTP API 与后台作业位于 `src/xhs_agent/web/`。任务、版本、图片上传、画像、模型设置、账号、发布预检与人工回执均已接入。本文保留设计依据；实际启动和接口实现范围见 [Web 使用说明](../web/README.md)。

## 定位与视觉

用户的主线是“表达需求 → 挑选方向 → 编辑内容 → 审核 → 确认发布”。界面围绕一篇内容的进度、产物和下一步操作组织。Agent、Skill 和模型配置放在辅助信息与设置页，主流程使用用户熟悉的业务名称。

原型位于 `web/prototype/`，可独立打开，使用明确标记的演示数据。页面中的模拟操作不连接真实服务。视觉采用编辑工作室的方向：暖白纸面、深绿侧栏、中文衬线标题，朱红只强调主要操作；审核提醒与提交结果不明使用琥珀色，已核实结果使用绿色，并保留文字标签。

## 页面结构

| 页面 | 主要内容与操作 |
| --- | --- |
| 创作工作台 | 任务搜索/筛选、阶段进度、候选选题、编辑与审核、右侧画像/问题/预览 |
| 内容归档 | 已确认发布的版本、作品链接、核实方式、文案导出 |
| 创作画像 | 名称、定位、受众、风格、真实经历、偏好、表达边界 |
| 发布账号 | 平台账号、本地账号 ID、绑定身份、实际登录校验与能力范围 |
| 技能与模型 | 各角色可用技能、模型服务商、模型 ID、API Key 保存替换清除及环境变量兼容 |

桌面工作台使用三栏：左侧任务列表，中间业务操作，右侧辅助信息。中等屏幕把辅助信息移到编辑区下方；手机端任务列表改成横向卡片，编辑区全宽。当前阶段只有一个主操作，发布入口随任务状态变化。

## 一篇内容的交互

### 1. 创建

必填字段只有本次创作目标，选择一个创作画像。内容形式提供分享、攻略、观点、记录、测评；素材和约束可逐步展开填写。热点是可选输入，首版展示手动提供的标题、来源和时间，不展示伪造的“实时热度”。

### 2. 选择方向

候选卡片展示标题、切入角度、为什么适合本次需求、画像匹配、需要补充的材料。用户明确选中后再进入资料和创作阶段。需要区分模型正在执行与等待用户选择，不能仅用一个“生成中”覆盖两者。

### 3. 编辑与审核

中间提供正文编辑、素材与依据、版本记录。右侧保留画像快照、审核问题及笔记预览。输入时显示未保存状态，保存产生新版本并撤销旧批准，重新经过审核；未保存时不能直接批准或发布。切换任务时提示处理未保存内容。

已有版本以只读方式查看，编辑操作始终针对当前草稿。替换图片同样生成新版本。预览帮助检查阅读效果，实际事实、个人体验和图片授权仍由创作者确认。

### 4. 提交与核实

发布确认框同时列出平台、目标账号、内容版本、标题和图片。提交期间禁用重复提交和内容修改。页面获得提交提示后进入“已提交 · 待核实”，不直接进入内容归档；只有得到平台核实或用户明确登记人工回执后才显示已确认发布。

| 后端状态 | 页面显示 | 主要操作 |
| --- | --- | --- |
| 后台作业正在执行选题 | 正在准备候选方向 | 查看进度，等待执行 |
| `ideating` | 待选择选题 | 采用一个方向 |
| `researching` / `researched` | 正在整理资料/创作 | 查看阶段产物与进度 |
| `pending_review` | 待你审核 | 编辑、保存新版本、提修改意见、批准或取消 |
| `approved` | 已批准 · 待发布 | 导出、修改、取消、明确选择目标发布 |
| `submitting` | 正在提交 | 等待结果；中断后由恢复流程处理 |
| `submitted` | 已提交 · 待核实 | 查看回执、核实平台结果 |
| `unknown` | 提交结果不明 | 核实平台结果；禁止盲目再次提交 |
| `published` | 已确认发布 | 查看作品与已发布版本、归档 |
| `failed` | 执行失败 | 显示可理解的原因，修复后重试 |
| `cancelled` | 已取消 | 查看记录 |

`TaskView.status` 与后台作业状态要分开表达。当前 `ideating` 在选题已经生成后写入，表示等待人工选择；Web 不能据此显示“模型还在生成”。

## 与现有 Python 项目衔接

正式前端建议采用 React + TypeScript，以 Vite 构建本地工作台。它适合此处与独立 Python 后端配合的客户端页面；路由、请求缓存和样式需明确选择，构建工具本身不提供这些业务层。[React 官方说明](https://react.dev/learn/build-a-react-app-from-scratch)

新增 HTTP API 层包装 `TaskService`，保留 LangGraph 管理人工中断、阶段路由、版本和检查点。前端只调用业务动作，不直接操作 SQLite 或拼接 LangGraph 状态。

```text
React 页面
    ├── HTTP 请求：查询、创建、选择、编辑、批准、发布
    └── SSE：接收作业和任务状态事件
            ↓
Python API + 后台作业执行器
            ↓
TaskService / SkillLibrary / AccountService
            ↓
LangGraph → Agent → LLMProvider / 平台连接器
```

状态和进度建议使用 SSE，用户操作继续用 HTTP。`EventSource` 适合服务端向浏览器单向推送状态；连接恢复后仍重新查询任务快照，事件不是唯一真相。[MDN SSE 文档](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)

### 建议的首版接口

以下是首版接口设计，现已由 FastAPI 提供（账号路径实际使用 platform/account_id 两段标识）：

| 接口 | 对应功能 |
| --- | --- |
| `GET /api/tasks` | 分页查询、状态筛选、搜索 |
| `POST /api/tasks` | 登记任务并提交后台执行，返回 202 和作业信息 |
| `GET /api/tasks/{id}` | TaskView、图检查点、人工暂停、后台作业和允许操作 |
| `GET /api/tasks/{id}/workflow` | 图运行状态、暂停 ID 与允许操作 |
| `GET /api/tasks/{id}/ideas` | 查询候选选题 |
| `POST /api/tasks/{id}/select` | 选择候选项，后台继续执行 |
| `POST /api/tasks/{id}/drafts` | 提交完整的新版本内容与媒体引用 |
| `POST /api/tasks/{id}/changes` | 提交修改意见，后台继续执行 |
| `POST /api/tasks/{id}/approve` | 批准指定当前版本 |
| `POST /api/tasks/{id}/preflight` | 发布前检查目标账号、版本和素材 |
| `POST /api/tasks/{id}/publish` | 明确目标平台和账号，提交发布作业 |
| `POST /api/tasks/{id}/confirm-published` | 登记人工核实回执 |
| `POST /api/tasks/{id}/retry`、`cancel` | 重试失败或中断任务、取消可取消任务 |
| `POST /api/tasks/{id}/reconcile` | 根据安全的人工检查点恢复待办状态，不执行图节点 |
| `POST /api/media` | 接收本地图片并返回服务端媒体引用 |
| `GET/POST /api/profiles` | 保存和选择可复用画像 |
| `GET/POST /api/accounts` | 账号列表和登记 |
| `POST /api/accounts/{id}/login`、`whoami` | 启动本地登录作业与实际身份校验 |
| `GET /api/skills?role=...` | 查询角色技能和授权范围 |
| `GET/PUT /api/settings/ideation` | 读取和保存选题模型配置及凭据引用 |
| `GET /api/jobs/{id}`、`GET /api/jobs/{id}/events` | 作业快照及 SSE 事件 |

接口层返回由检查点与业务约束共同决定的 `allowed_actions`，前端据此启用按钮，后端在执行动作时再次验证状态、版本和暂停位置。人工恢复请求携带预期版本与 `interrupt_id`，过期操作返回 409 后刷新任务；服务层按 ID 执行 `Command(resume=...)`。媒体由服务端管理，不能把浏览器显示的文件名直接当成后端图片路径。

### 后端实施要点（第一版已按此接入）

1. **后台执行入口**：`TaskService` 已拆分 `register_task/start_task`，同步 CLI 仍可使用 `create_task()`。Web 先持久化任务和作业，再由执行器调用图；同一任务同时只允许一个活动写作业。浏览器刷新或 HTTP 重试使用原请求 ID，不重复发起同一提交。
2. **查询和画像存储**：补齐任务列表、分页、历史草稿查询和画像 CRUD，继续保留每个任务的输入快照。
3. **进度事件**：记录作业开始、阶段变化、授权技能加载结果和最终状态。可以显示工具名称与执行摘要，避免把模型内部推理当成产品日志。
4. **本地登录作业**：首版本地运行，登录按钮打开后端所在机器的浏览器窗口，用户完成扫码后刷新绑定结果。现有连接器没有 Web 页内二维码接口，原型对此只展示流程说明。
5. **配置与凭据边界**：支持密码框直接填写模型 API Key，在服务端单独加密保存；响应只返回配置状态，留空保留、输入替换、明确勾选清除。凭据绑定服务商和接口地址，环境变量方式继续兼容。浏览器 Cookie 留在服务端。只有选题实际接入模型，其余 Mock 能力应在界面中准确标识。

## 实施顺序

首版先完成任务列表、新建任务、候选选题、正文编辑、审核、画像和模型设置，把“模型选题到人工审核”跑通；第二步接入媒体上传、账号登录、发布预检与结果核实；最后补充技能授权管理、比较版本和执行记录。数据分析、定时发布、多平台批量分发等能力等对应后端实现后再开放。

原型用于设计参考。第一版正式页面已以服务端状态、实际审核和发布回执为准，原型的浏览器数据不导入业务记录。
